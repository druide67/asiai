# Apple Silicon で Qwen3.8-27B にどのエンジンを選ぶか

モデルの問題は決着している。Qwen3.8-27B はノートパソコンで動作し、262,144 トークンの
コンテキストを保持する。エンジンの問題は決着しておらず、そのコストは考えられているより
大きい。

8つのエンジンを1台の M5 Max で計測した。最も興味深い2つの結果は、そもそも速度の話では
ない。*同一のファイル* を読む2つのエンジンが 50% 食い違うこと、そして誰も有効にしない
フラグのことである。

## 数字の前に、条件

M5 Max 128 GB、AC 電源、High Power Mode、常駐するエンジンは同時に1つのみ。エンジン同士を
比較できるよう、すべてのエンジンで reasoning(思考)を無効化した。すべてのセルで 1-2 分
以内にサーマルスロットリングにより 50% まで低下する — **これらは下限値であって、最大値
ではない**。出力妥当性は全行で 100%。プロンプトサイズは 7,530 トークン(短いフェーズ)と
55,839(長いフェーズ)、出力上限は 400 および 200 トークン。

**これがあなたの環境で得られる速度だとは主張しない。** 主張するのは、単一のプロトコルの
下でのエンジン間の差である。

⁽¹⁾ と ⁽²⁾ は **バイト単位で同一の重みファイル** を共有する行を示す。各行は1セル、
1エクスポートであり、実行間で値を混ぜていない。

⚠️ **メモリはファミリーをまたいで比較できない。** llama.cpp と Ollama は GGUF を mmap
する。常駐セットはファイルバックドで退避可能である(llama.cpp: RSS 36.8 GB に対し物理
フットプリントは 19.8 GB)。MLX 系エンジンはアロケートする。この列はファミリー内で読み、
ファミリーをまたいで読まないこと。

⚠️ **宣言コンテキストは一様ではない。** 3つのエンジンには明示的なウィンドウを与え、
残りは既定値で動かした。それだけでメモリ列を全体で順位付けすることは禁じられる。

## 2つのエンジン、1つのファイル、50% の差 ⁽¹⁾

mlx-vlm、mlx-lm、rapid-mlx はいずれも `lmstudio-community/Qwen3.8-27B-MLX-4bit` の
スナップショット `6067b15c` を提供した — ディスク上では同一のファイルである。

| エンジン | ウォーム | 初トークン | メモリ |
|---|---|---|---|
| mlx-vlm + MTP ドラフター | **43.3** | 9,982 ms | 15.5 GB |
| rapid-mlx | 30.2 | 33,195 ms | 15.0 GB |
| mlx-lm | 28.8 | **432 ms** | 14.6 GB |

**mlx-lm から mlx-vlm へ +50%、サーバー以外は何も変えていない。** これは本キャンペーンで
最もクリーンな比較である。量子化の違いを持ち出して議論する余地がない。

そしてそれは即座に反転する。mlx-vlm の 50% の優位は **23倍悪い初トークン時間** を代償と
する。プレフィックスキャッシュを一切持たないからだ。ワンショットの生成であれば勝つ。
エージェント用途では使い物にならない — その理由は次節にある。

## 20% を稼ぐフラグと、それが無効である理由 ⁽²⁾

Qwen3.8 は **重みの中にマルチトークン予測ヘッドを同梱している**。モデルが数トークン先を
提案し、エンジンが1回のフォワードパスでそれを検証する。確率比による受理規則を実装する
エンジンは出力分布を厳密に保存する。我々自身はその性質を検証していないし、ベンチマークの
言うことを鵜呑みにすべきでもない — 自分の使うエンジンの実装を読むこと。

ほぼすべてのエンジンが **無効** の状態で出荷している。

| エンジン | フラグ | 既定で有効か |
|---|---|---|
| vmlx | `--native-mtp-depth` | **はい** |
| MTPLX | `--mtp --depth 3` | はい |
| vllm-mlx | `--enable-mtp` | いいえ |
| llama.cpp | `--spec-type draft-mtp` | いいえ |
| LM Studio | `--speculative-draft-mtp` | いいえ |
| mlx-vlm | `--draft-kind mtp` + 別途ドラフター用リポジトリ | いいえ |
| oMLX | 我々の実行では Qwen3.8 で作動しなかった | — |
| Ollama · mlx-lm · rapid-mlx | 非対応 | — |

これを知らないことのコストを、同じ重みファイル、同じ 65,536 コンテキスト、2つのフラグ
以外はすべて同じ条件で計測した: **LM Studio は 23.1 → 27.8 tok/s、+20%。** これを提示
する GUI は存在しない。

二次的な効果、そしてこちらの方が重要である: **2つのエンジンをそれぞれの既定値で比較する
ことは、2つの異なるレジームを比較することである。** vmlx はドラフトを行い、llama.cpp は
行わない。

## 初トークンは 350倍の幅がある。プリフィルでは説明できない。

表全体で 99 ms から 33,195 ms まで。決め手は **プレフィックスキャッシュの粒度** である —
繰り返されるプロンプトのうち、ターン間でどれだけが生き残るか。同一フェーズ(初トークン
遅延を取得するウォームターン)で計測した:

| エンジン | 再利用 | 毎ターン再プリフィル | 初トークン |
|---|---|---|---|
| llama.cpp | 7,526 / 7,530 — **トークン単位** | 4 トークン | 125 ms |
| oMLX | 6,144 / 7,530 — **1024 トークンのブロック単位** | 1,386 トークン | 1,944 ms |
| mlx-vlm | 0 / 7,530 | 7,530 トークン | 9,982 ms |

6,144 は 1,024 の6倍である。oMLX はブロック単位でまとめて再利用し、1ブロックを満たさない
ものはすべて再プリフィルする — 毎ターン、永久に 1,386 トークン。125 ms と 2 秒 の差は、
すべてこれで説明がつく。

⚠️ **セッション集計の再利用率をエンジン間で比較してはならない。** テストプロンプトの
うちキャッシュ可能な割合に応じて上限が異なり、比較すると、同一フェーズで比べた途端に
消えるパラドックスが生じる。本ページの以前の草稿で、我々はその誤りを犯した。

プリフィルスループットの列は **公開しない**。我々の値は繰り返しのないコールドリクエスト
1回から得たもので、遅延ロードするエンジンでは 20 GB をディスクから読む処理を含む —
LM Studio はそのリクエストで 216 tok/s、その直後のリクエストで 938 を計測した。捏造した
数字になっていただろう。

## トークン毎秒は速度ではない

同一モデルの量子化どうしを比べると、tok/s は出力がどれだけ速く届くかではなく、出力が
どれだけ長いかを部分的に測っている:

| ビルド | tok/s | chars/s |
|---|---|---|
| Bare-Speed | 56.0 | 200.8 |
| Optimized-Speed | 44.4 | **203.1** |
| Optimized-Quality | 40.8 | 165.7 |

Bare-Speed はトークン毎秒で 26% リードしながら、文字毎秒では **負けている**。3つとも
トークナイザーは同じであり、違うのは量子化が何を書くことを選んだかである。数字は定義と
一緒に公開すること。

## 我々の推奨

**ローカルの自律エージェント向け: MTPLX と `Qwen3.8-27B-MTPLX-Optimized-Speed`、MTP は
depth 3。** 高速、初トークンまで 99 ms、トークン単位のプレフィックス再利用、27 GB。

Bare-Speed は選ばない。数値上は先行しているが、3 つのビルドは bf16 からの乖離度が異なる。
量子化作者が公開した値は Optimized-Quality が **0.00105**、Optimized-Speed が **0.0220**、
Bare-Speed が **0.0376**。彼の測定であって我々のものではなく、再現もしていない — しかし
誰もが持ちうる唯一の忠実度の数値であり、Bare-Speed は Quality から一桁離れている。

Optimized-Quality も選ばない。誰もタスク上で実証していない優位のために **8.3 GB 多く**
消費する。

**推論を有効にして動かすこと。** Qwen はエージェント用途に `xhigh` の努力レベルを推奨して
おり、マルチターンのエージェントタスクでは努力レベルを下げると*「分析が不十分になり、失敗
や再試行が増え、総レイテンシが増加しうる」*と述べている。MTPLX 2.7.1 も別途、推論を無効に
することを Qwen3.8 の既知の問題として挙げている。なお `high` はこのモデルには存在しない —
Qwen が公開しているのは `low`、`medium`、`xhigh` のみで、既定値は `xhigh` である。

## 測定できなかったこと

**vmlx と vllm-mlx は試みたが、欠けている。** どちらもネイティブ MTP に対応しており —
vmlx は既定で有効 — その不在は本比較における実質的な欠落であって、丸め誤差ではない。
vllm-mlx はコマンドラインのクォートのエラーで起動時に落ちた。vmlx は本稿の公開時点で
まだ実行中だった。

**エンジン同士を比較可能にするため、推論は全体を通じて無効にした。** これは計測上の判断
であって配備上の判断ではない — 上記の推奨を参照。推論がこれらのエンジンに何をもたらすかに
ついて提示できる数値はなく、外挿するつもりもない。

**バージョンに関する留保。** MTPLX の行は **2.6.0** で実行した。エンジンが `qwen3_8` の
モデルファミリーを搭載する前であり、Qwen3.6 の既定値で Qwen3.8 を提供していた — サンプ
リング契約も異なる。これはスループットには影響しないが、挙動に関するあらゆる点には影響
する。oMLX の行は一時的な開発ビルドから実行され、そのバージョン文字列をエクスポートが
捕捉していないため、この行は公開されたままでは再現できない。また我々の mlx-vlm の
エクスポートは自身を `mlxlm 0.31.3_2` と名乗る — サーバーが `mlx_vlm.server` であった
ことを証明するのは起動ログだけである。

**3つの MTPLX ビルド間の初トークンの順位は、それ自身のノイズの内側にある** — この指標の
変動係数は 0.33 から 0.66。99、101、118 ms は分離できない。スループットの列ははるかに
安定している(CV 0.01-0.04)。

**同一コマンドの再実行における再テストのばらつきは 7.5% に達し**(Optimized-Quality の
3回の実行で 37.97 / 40.82 / 39.35 tok/s)、メモリは再実行の間で 5 GB 動いた。8% 未満の
差はすべて、無いものとして扱うこと。

**チューニングは対称ではなかった。** llama.cpp には明示的なキャッシュのフラグ
(`--cache-reuse 256 --slot-prompt-similarity 0.5`、flash attention、131k KV)を与えたが、
MLX 系エンジンには与えていない。MTPLX は既定値ではなく `--profile turbo` で実行した。
これは我々が実際にデプロイする構成どうしの比較であって、箱出しの既定値どうしの比較では
ない。

## 再現方法

すべての数字は [asiai](https://asiai.dev) が生成した認証済みカードに由来し、孤立ゲート、
提供モデルの同一性証明、サーマルサンプリングを備えた単一のスクリプト化された経路を通って
いる。生のエクスポートも入手可能。

1つだけ持ち帰るなら: **自分のエンジンがマルチトークン予測を持つか、そしてそれが有効に
なっているかを確認すること。**
