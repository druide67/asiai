# Apple Silicon 上 Qwen3.8-27B 该用哪个引擎

模型的问题已经有答案:Qwen3.8-27B 能在笔记本上运行,并且能容纳 262,144 个 token 的上下文。
引擎的问题还没有答案,而它的代价比大多数人以为的要大。

我们在同一台 M5 Max 上测量了八个引擎。最有意思的两个结果与速度完全无关 —— 一个是两个引擎读取
*同一份文件*却相差 50%,另一个是一个没人打开的开关。

## 先说条件,再说数字

M5 Max 128 GB,接市电,High Power Mode,同一时刻只驻留一个引擎。所有引擎都关闭了推理,以便相互
比较。每一个测量单元都在 1-2 分钟内因过热降频到 50% —— **这些是下限,不是上限**。每一行的输出
有效率都是 100%。提示词长度为 7,530 token(短阶段)和 55,839(长阶段),输出上限分别为 400 和
200 token。

**我们并不声称这就是你会得到的速度。** 我们声称的是:在同一套协议下,这些是引擎之间的差距。

## 表格

| 引擎 | 权重 | n | 热态 | 56k 时 | 首 token | 内存 | 声明的上下文 |
|---|---|---|---|---|---|---|---|
| **MTPLX** Bare-Speed | MTPLX 4-bit g64 | 3 | **56.0** | **46.5** | 101 ms | 22.0 GB | 引擎默认值 |
| **MTPLX** Optimized-Speed | MTPLX 4-bit g32 | **5** | **44.4** | 37.5 | 99 ms | 27.0 GB | 引擎默认值 |
| **mlx-vlm** + MTP 草稿模型 | MLX 4-bit ⁽¹⁾ | 3 | **43.3** | 28.9 | **9,982 ms** | 15.5 GB | 引擎默认值 |
| **MTPLX** Optimized-Quality | MTPLX 8-bit g64 | 3 | 40.8 | 30.3 | 118 ms | 32.9 GB | 引擎默认值 |
| Ollama 0.32.13 | GGUF(未声明) | 3 | 32.8 | 21.7 | 240 ms | 30.3 GB | 65,536 |
| llama.cpp b10434 + MTP | GGUF Q5_K_XL ⁽²⁾ | 3 | 31.8 | 22.7 | **125 ms** | 36.8 GB | 131,072 |
| rapid-mlx 0.12.11 | MLX 4-bit ⁽¹⁾ | 3 | 30.2 | 24.7 | **33,195 ms** | 15.0 GB | 引擎默认值 |
| oMLX 0.6.0-dev | oQ4e-mtp(第三方) | 3 | 29.8 | 24.6 | 1,968 ms | 16.7 GB | 引擎默认值 |
| mlx-lm 0.31.3 | MLX 4-bit ⁽¹⁾ | 3 | 28.8 | 24.0 | 432 ms | **14.6 GB** | 引擎默认值 |
| LM Studio 0.4.21 **+ MTP** | GGUF Q5_K_XL ⁽²⁾ | 3 | 27.8 | 23.4 | 419 ms | 36.3 GB | 65,536 |
| LM Studio 0.4.21 默认配置 | GGUF Q5_K_XL ⁽²⁾ | 3 | 23.1 | 18.7 | 359 ms | 35.2 GB | 65,536 |

⁽¹⁾ 和 ⁽²⁾ 标记的是共用**逐字节相同的权重文件**的行。每一行都是一个测量单元、一次导出 ——
没有任何数值在不同运行之间被混用。

⚠️ **内存在不同家族之间不可比。** llama.cpp 和 Ollama 用 mmap 映射它们的 GGUF:它们的常驻集由
文件支撑,可被回收(llama.cpp:36.8 GB RSS,但物理占用为 19.8 GB)。MLX 系引擎则是直接分配。
这一列要在同一家族内部读,不要跨家族读。

⚠️ **声明的上下文各不相同。** 有三个引擎被显式指定了窗口,其余的跑在各自的默认值上。仅凭这一点,
就不允许对内存这一列做全局排名。

## 两个引擎,同一份文件,相差 50% ⁽¹⁾

mlx-vlm、mlx-lm 和 rapid-mlx 服务的都是 `lmstudio-community/Qwen3.8-27B-MLX-4bit`,快照
`6067b15c` —— 磁盘上的同一份文件。

| 引擎 | 热态 | 首 token | 内存 |
|---|---|---|---|
| mlx-vlm + MTP 草稿模型 | **43.3** | 9,982 ms | 15.5 GB |
| rapid-mlx | 30.2 | 33,195 ms | 15.0 GB |
| mlx-lm | 28.8 | **432 ms** | 14.6 GB |

**从 mlx-lm 到 mlx-vlm 提升 +50%,除了服务端什么都没改。** 这是整轮测量中最干净的对比:没有
量化差异可以争论。

而它立刻就反转:mlx-vlm 这 50% 的优势,代价是**首 token 时间差 23 倍**,因为它根本没有前缀缓存。
对于一次性生成,它赢。对于智能体,它无法使用 —— 原因在下一节。

## 那个能带来 20% 的开关,以及它为什么是关的 ⁽²⁾

Qwen3.8 在**权重内部自带一个多 token 预测头**。模型一次提前给出若干个 token,引擎在一次前向
传播中验证它们。实现了概率比接受规则的引擎能够精确保持输出分布;这一性质我们自己没有验证过,
你也不应该因为一份基准测试就信以为真 —— 去读你所用引擎的实现。

几乎每个引擎出厂时都把它**关着**。

| 引擎 | 开关 | 默认开启? |
|---|---|---|
| vmlx | `--native-mtp-depth` | **是** |
| MTPLX | `--mtp --depth 3` | 是 |
| vllm-mlx | `--enable-mtp` | 否 |
| llama.cpp | `--spec-type draft-mtp` | 否 |
| LM Studio | `--speculative-draft-mtp` | 否 |
| mlx-vlm | `--draft-kind mtp` + 独立的草稿模型仓库 | 否 |
| oMLX | 在我们的运行中没有对 Qwen3.8 生效 | — |
| Ollama · mlx-lm · rapid-mlx | 不支持 | — |

我们在同一份权重文件、同样的 65,536 上下文、除两个开关外完全相同的条件下,测量了“不知道这件事”
的代价:**LM Studio 从 23.1 提升到 27.8 tok/s,+20%。** 没有任何图形界面把它暴露出来。

二阶效应,而且更重要:**在各自默认配置下比较两个引擎,比较的是两种不同的工作机制。** vmlx 会做
草稿预测,llama.cpp 不会。

## 首 token 相差 350 倍。预填充解释不了这件事。

整张表从 99 ms 到 33,195 ms。起决定作用的是**前缀缓存的粒度** —— 重复的提示词中有多少能在两轮
之间存活下来。测量取自同一个阶段(热态那一轮,首 token 延迟就是在那里取的):

| 引擎 | 复用 | 每轮重新预填充 | 首 token |
|---|---|---|---|
| llama.cpp | 7,526 / 7,530 —— **token 级** | 4 个 token | 125 ms |
| oMLX | 6,144 / 7,530 —— **1024 token 的块** | 1,386 个 token | 1,944 ms |
| mlx-vlm | 0 / 7,530 | 7,530 个 token | 9,982 ms |

6,144 是 1,024 的六倍。oMLX 只复用完整的块,凑不满一块的部分一律重新预填充 —— 1,386 个 token,
每一轮,永远如此。125 ms 与 2 秒之间的全部差距就在这里。

⚠️ **不要在引擎之间比较会话级汇总的复用率。** 它们的上限取决于测试提示词中有多少是可缓存的,
各不相同;比较它们会产生一些悖论,而当你改为比较同一个阶段时,这些悖论就消失了。本页较早的一版
草稿中我们就犯过这个错误。

我们**不**发布预填充吞吐这一列。我们的数据来自单次、未重复的冷请求,而对于惰性加载的引擎,这里面
还包含从磁盘读取 20 GB —— LM Studio 在那次请求上测得 216 tok/s,在紧接着的下一次上测得 938。
那会是一个捏造出来的数字。

## 每秒 token 数不是速度

在同一模型的不同量化之间,tok/s 有一部分测的是输出有多长,而不是它们到达得有多快:

| 构建 | tok/s | chars/s |
|---|---|---|
| Bare-Speed | 56.0 | 200.8 |
| Optimized-Speed | 44.4 | **203.1** |
| Optimized-Quality | 40.8 | 165.7 |

Bare-Speed 在每秒 token 数上领先 26%,在每秒字符数上却**落后**。三者用的是同一个分词器 ——
不同的是各个量化选择写出了什么。发布数字时,请把它的定义一起发布。

## 我们的建议

**用于本地自主智能体:MTPLX 配 `Qwen3.8-27B-MTPLX-Optimized-Speed`,MTP 深度 3。** 快,首 token
99 ms,token 级前缀复用,27 GB。

不选 Bare-Speed,尽管它在纸面上领先。工具调用测试套件,三者使用同一套协议:

| 构建 | 工具调用(24 轮) | 压力测试(33 轮) | 编辑轮次(9) |
|---|---|---|---|
| Optimized-Quality | **83.3%** | 81.8% | **55.6%** |
| Optimized-Speed | 79.2% | **81.8%** | 44.4% |
| Bare-Speed | 62.5% | 72.7% | 22.2% |

⚠️ **请诚实地读这些数字。** 在更大的压力测试套件上,Optimized-Speed 与 Optimized-Quality
**完全打平**。而对 24 轮套件做 Fisher 精确检验,Bare-Speed 对 Optimized-Speed 得到
**p = 0.34**,Quality 对 Speed 得到 **p = 1.00** —— 在这个样本量下,两个差距都不具有统计
显著性。这 24 轮是 8 个任务重复 3 次,所以有效 n 还要更小。

我们真正掌握的,是**跨三个套件、两种独立方法的一致方向**:我们的工具调用结果对三个构建的排序,
与量化作者公布的与 bf16 的偏离度数字给出的排序相同(0.00105 / 0.0220 / 0.0376 —— 是他的测量,
不是我们的,我们也没有复现)。互不相关的方法之间取得一致,比其中任何一个 p 值都更有价值。这就是
我们不推荐 Bare-Speed 的理由,而它作为证据,比一张百分比表格看上去要弱。

也不选 Optimized-Quality:为了一个我们无法证明的优势,它要多花 **8.3 GB**。

## 我们没能测到的

**vmlx 和 vllm-mlx 都尝试过,但缺席。** 两者都支持原生 MTP —— vmlx 还默认开启 —— 所以它们的
缺席是这次对比中一个真实的缺口,不是一个舍入误差。vllm-mlx 因为一个命令行引号错误在启动时失败;
vmlx 在本文发出时仍在运行中。

**推理被关闭了,而这并不是你应该运行这个模型的方式。** Qwen 表示,在多轮智能体任务中,较低的
推理强度 *"can lead to insufficient analysis, more failures, and repeated retries, which may
increase total latency"*(可能导致分析不足、失败增多、反复重试,从而增加总延迟)。MTPLX 2.7.1
把关闭推理列为 Qwen3.8 的一个已知问题。我们关闭它是为了让引擎之间可比 —— 这是一个测量上的决定,
不是一个部署上的决定。

**版本方面的保留。** MTPLX 的各行跑在 **2.6.0** 上,当时该引擎还没有提供 `qwen3_8` 模型家族 ——
它是按 Qwen3.6 的默认值来服务 Qwen3.8 的,其中包括一套不同的采样约定。这不影响吞吐;但凡是与
行为有关的,它都影响。oMLX 那一行来自一个临时的开发构建,导出没有捕获到它的版本字符串,所以按
发布的形式,那一行不可复现。另外,我们的 mlx-vlm 导出把自己标识为 `mlxlm 0.31.3_2` —— 只有
启动日志能证明服务端是 `mlx_vlm.server`。

**三个 MTPLX 构建之间的首 token 排名落在它自身的噪声之内** —— 该指标的变异系数在 0.33 到 0.66
之间。99、101 和 118 ms 无法区分。吞吐那一列要稳定得多(CV 0.01-0.04)。

**同一条命令完全相同地重跑之间,重测离散度达到 7.5%**(Optimized-Quality 的三次运行分别为
37.97 / 40.82 / 39.35 tok/s),内存在两次重跑之间变动了 5 GB。任何低于 8% 的差距都当作不存在。

**调优并不对称。** llama.cpp 拿到了显式的缓存开关(`--cache-reuse 256
--slot-prompt-similarity 0.5`、flash attention、131k KV),而 MLX 系引擎没有。MTPLX 跑在
`--profile turbo` 上,不是它的默认值。这是一次对我们会实际部署的配置的比较,不是对开箱默认值的
比较。

## 如何复现

每一个数字都来自 [asiai](https://asiai.dev) 生成的认证卡片,经由单一的脚本化路径产出,带有独占
门禁、所服务模型的身份证明和热量采样。原始导出可提供。

如果只记住一件事:**检查你的引擎有没有多 token 预测,以及它是否开着。**
